# Numbers and precision

## While a formula runs

Numeric literals keep their written decimal digits. Decimal-bearing arithmetic (`+`, `-`, `*`, `/`, and powers with whole exponents), comparisons and number functions use the shared fixed-point helper when the written decimals fit within 15 significant digits; whole-number `+`, `-`, `*`, and divisible `/` keep their exact BigInt path up to 400 digits. Longer decimals and short decimals mixed with a whole number above 2^53 keep the existing double path. Results past the 400-digit limit are `?`. For example, `0.1 + 0.2` is `0.3`, `123.45 - 123` is `0.45`, and `Div ( 0.7 ; 0.1 )` is `7`. `1 / 3` keeps its existing 16-significant-digit result. `Sum` and `Average` keep every digit of their decimal inputs (`Sum ( 0.1234567890123456 )` is `0.1234567890123456`, `Sum ( 1234.5678901234567 )` is `1234.5678901234567`); whole-number sums and averages retain every digit when their result is whole, while an average that does not divide exactly keeps its existing double result (`Average ( 100000000000000000007 ; 100000000000000000008 )` is `100000000000000000000`). `Variance`, `VarianceP`, `StDev` and `StDevP` add their values with the same decimal sum (`Variance ( 0.1 ; 0.2 ; 0.3 )` is `0.01`). `Round`, `Truncate`, `Int`, `Ceiling`, `Floor`, `Abs`, `Mod`, `Div`, `Max`, `Min`, comparisons, `GetAsNumber`, number-to-text conversion and `SerialIncrement` share the exact integer or fixed-point representation where their inputs support it. `SerialIncrement` returns `?` for an amount that is not a finite whole number the engine holds exactly (`1/0`, `1e30`) and for a digit run longer than 400 digits. `NumToJText` returns `?` for a non-finite separator or style and, with separator style 2 or 3, for a number of more than 20 digits (the units stop at 京). The store's increment of a prefixed or suffixed serial number (`ID-9007199254740992`) also adds to its digit run exactly. `SetPrecision` can format a repeating result to the requested number of decimal places. Custom functions that return a recursive call through `If`, `Case` or `Let` use an explicit loop and reach the 10,000-call limit. Non-tail custom recursion still uses the JavaScript call stack: the generated `Sum1 ( n ) = If ( n <= 0 ; 0 ; n + Sum1 ( n - 1 ) )` test succeeds at 500 levels inside the test suite, while 5,000 levels returns `?` on this Node build. The failure point varies with the stack available to the process and with how warm the code is: a fresh process running only that formula stopped at about 480 levels. Support for deeper non-tail recursion is not implemented; see [the recursion-depth research note](research/recursion-depth.md). ## What is stored

In a synthetic store, writing `9007199254740993` and reading it through `Store.get` returned `9007199254740992`; writing `12345678901234567890` returned `12345678901234567000`. This shows precision was lost by the store's number-field read path. FileMaker's own storage result is unverified. <!-- known-difference: SQL and calculations ;; Number-field storage reads lose digits beyond double precision ;; Reading back 9007199254740993 yielded 9007199254740992 and a 20-digit input yielded a rounded value ;; Repeat the generated-store write and read in FileMaker to determine whether its stored value differs -->

Text written to a number field that is not in decimal notation (`0x10`, `0b101`, `0o17`, `1_000`, `12abc`) is kept as the text and not turned into a number; thousands separators, a leading sign and an exponent are accepted (`1,234.5` is `1234.5`). Whether FileMaker keeps such text in a number field is not checked. <!-- known-difference: SQL and calculations ;; Text written to a number field that is not in decimal notation (0x10, 0b101, 12abc) is kept as the text, and whether FileMaker keeps it is not checked ;; Such a value reads back as the text it was written as, not as a number ;; A FileMaker run that types 0x10 into a number field -->

## What leaves the server

The Data API serializes record field data as JSON. Because the store read path already returned rounded JavaScript numbers, a JSON client receives rounded digits for these inputs; this is an inference from the store probe and serialization path, not an end-to-end HTTP probe. The web client's display path formats JavaScript numbers with `Intl.NumberFormat` and at most two fraction digits; this is an implementation observation, not a rendered-page probe. The SQL wire formats numeric values as text and has a binary numeric encoding, but the exact output for stored `1e21` and a 20-digit field value was not probed end to end.
