# Numbers and precision

## While a formula runs

Calculations use JavaScript numbers (binary doubles) for ordinary numeric values. The `+`, `-` and `*` operators also preserve whole-number arithmetic exactly while the result has at most 400 digits; beyond that limit they return `?`. Decimal arithmetic has special handling, so common decimal operations such as `0.1 + 0.2` produce `0.3`. `+` and `-` of two numbers written with up to 15 decimal places give the result with no more places than the longer of the two when it fits in 15 digits, so `123.45 - 123` is `0.45` and not the `0.4500000000000028` that doubles give; an operand with more places (`1 / 3`) or a result past 15 digits is left to the general handling. `Mod` and `Div` of decimals treat an exact decimal multiple as one (`Mod ( 0.7 ; 0.1 )` is `0`, `Div ( 0.7 ; 0.1 )` is `7`). `Sum` and `Average` preserve the decimal digits represented by their numeric inputs, including `Sum ( 0.1234567890123456 )` = `0.1234567890123456` and `Sum ( 1234.5678901234567 )` = `1234.5678901234567`; whole-number aggregates also preserve exact digits beyond 2^53 when their values remain representable by the calculation engine. `Variance`, `VarianceP`, `StDev` and `StDevP` use decimal-clean sums for their aggregate arithmetic (`Variance ( 0.1 ; 0.2 ; 0.3 )` is `0.01`). `SerialIncrement` adds exactly to a digit run of up to 400 digits and returns `?` for an amount that is not a finite whole number the engine holds exactly (`1/0`, `1e30`) and for a longer run; the store's prefixed and suffixed serial increment also uses exact integer arithmetic. `NumToJText` returns `?` for a non-finite separator or style and, with separator style 2 or 3, for a number of more than 20 digits (the units stop at 京). `Round`, `Truncate` and `SetPrecision` use decimal-aware calculation paths. `SetPrecision` can format a repeating result to the requested number of decimal places. Functions other than `+`, `-` and `*` may round values past 2^53 today. The current acceptance tests pin correct behaviours, and [whole-numbers.test.ts](../packages/calc/test/whole-numbers.test.ts) covers the existing large-integer cases without making every current loss permanent.

## What is stored

In a synthetic store, writing `9007199254740993` and reading it through `Store.get` returned `9007199254740992`; writing `12345678901234567890` returned `12345678901234567000`. This shows precision was lost by the store's number-field read path. ## What leaves the server

The Data API serializes record field data as JSON. Because the store read path already returned rounded JavaScript numbers, a JSON client receives rounded digits for these inputs; this is an inference from the store probe and serialization path, not an end-to-end HTTP probe. The web client's display path formats JavaScript numbers with `Intl.NumberFormat` and at most two fraction digits; this is an implementation observation, not a rendered-page probe. The SQL wire formats numeric values as text and has a binary numeric encoding, but the exact output for stored `1e21` and a 20-digit field value was not probed end to end.
